# 欢友完整优化方案

> 本方案根据 `欢友运行流程优化讨论.md` 收敛而来，用于后续开发实施。重点是减少 OCR 次数、减少截图次数、复用同一轮已识别结果，并保留完整回退能力。

## 1. 优化目标

- 减少每轮运行中的完整 `list OCR` 次数。
- 减少不必要的 `dialogue OCR`。
- 减少机械臂截图次数，尤其是连续截图。
- 提升从异常页面或主界面其他 tab 恢复到聊天列表的成功率。
- 保持现有模板选定范围机制，不重新设计模板匹配范围。
- 所有优化都必须可单独关闭、可统计耗时、可回退。

## 2. 不做和暂缓内容

- 不缓存“下一条”“发送”“麦克风”的跨轮坐标，这些按钮位置可能变化。
- 不缓存“新招呼”的跨轮坐标，只允许同一张截图内复用匹配结果。
- 不自动优化 points OCR 范围，points 范围由用户手动设置。
- 不做红点快速预筛，等客户环境测试完成后再决定。
- 不删除现有模板选定范围机制。
- 不在全屏范围内只靠“消息关系”判断聊天列表。

## 3. 配置开关

建议新增以下开关，默认可以先逐项开启测试：

```json
{
  "enable_runtime_coordinate_cache": true,
  "enable_screenshot_reuse": true,
  "enable_compact_list_ocr_region": true,
  "enable_dialogue_name_region": true,
  "enable_dialogue_message_region": true,
  "enable_next_new_greeting_fast_path": true,
  "enable_bottom_message_recovery": true
}
```

开关要求：

- 每个优化点必须可独立关闭。
- 任一小范围 OCR 失败后必须回退原有大范围逻辑。
- 任一缓存点击失败后只清理对应缓存，不清空全部缓存。

## 4. 运行态缓存

新增单设备、单线程运行态缓存，只在当前进程内有效，不写入配置文件。

```text
runtime_cache = {
  screen_anchors: {
    chat_list_title: (x, y),
    bottom_message: (x, y),
    bottom_my: (x, y)
  },
  template_points: {
    back: (x, y),
    input_box: (x, y)
  },
  current_frame_matches: {
    new_greeting: (x, y),
    next_message: (x, y),
    send: (x, y),
    microphone: (x, y)
  },
  ocr_regions: {
    bottom_nav_region: (left, top, right, bottom),
    list_compact: (left, top, right, bottom),
    dialogue_name: (left, top, right, bottom),
    dialogue_message: (left, top, right, bottom),
    points_configured: (left, top, right, bottom)
  },
  current_chat: {
    name: "...",
    name_point: (x, y),
    input_box_opened: true/false
  }
}
```

缓存失效条件：

- 线程重启。
- 点击后界面没有按预期变化。
- 连续 `StepUnavailable`。
- 缓存坐标对应模板即时校验失败。
- 用户暂停进程后重新启动。

不作为主动清缓存条件：

- 黑屏、无手机、未知界面恢复。
- 设备或 app 切换，因为用户必须暂停后重新启动。
- 截图尺寸变化，用户端正常不会发生。
- 用户重新设置模板范围，用户端不提供该入口。

## 5. 聊天列表判断

现有逻辑：

- 先用 `screen.chat_list` 模板判断聊天列表。

新增逻辑：

- 如果模板不确定，在当前 `screen.chat_list` 选定范围内做小区域 OCR。
- OCR 到“消息关系”时，直接判定当前为聊天列表。
- 不需要再结合底部“消息”或列表行二次确认。
- 该 OCR 只使用 `screen.chat_list` 的选定范围，不做全屏 OCR。

回退：

- 如果没有识别到“消息关系”，继续原有界面判断和恢复逻辑。

## 6. 底部消息恢复特例

场景：

- 程序进入欢友主界面的其他 tab，例如交友、广场、娱乐、我的。
- 当前不是聊天界面，也不是黑屏、无手机。
- 此时不应优先点返回，可以优先点底部“消息”恢复列表。

实现：

- 第一次完整 `list OCR` 成功识别到底部导航后，缓存 `bottom_nav_region`。
- 计算方式：

```text
bottom_nav_region_top = min(bottom_nav各项top) - 0.02
bottom_nav_region_bottom = max(bottom_nav各项bottom) + 0.02
bottom_nav_region = [0.0, top, 1.0, bottom - top]
```

- 偏移全部使用屏幕比例，不使用固定像素。
- 后续未知界面恢复前，如果已有 `bottom_nav_region`，只扫这个小区域。
- 小区域 OCR 识别到“消息”后，点击“消息”。
- 点击后重新截图，再用聊天列表模板或“消息关系”OCR 确认。

约束：

- 没有 `bottom_nav_region` 缓存时，不为了这个特例跑完整 `list OCR`。
- 未识别到“消息”时，继续原未知界面返回恢复。

## 7. 列表扫描顺序优化

当前流程：

```text
list OCR -> 点击底部消息 -> 截图 -> list OCR复扫 -> 选择未读目标
```

优化后：

```text
如果没有 bottom_message 缓存：
  list OCR -> 点击底部消息 -> 截图 -> list OCR复扫

如果已有 bottom_message 缓存：
  点击缓存底部消息 -> 截图 -> list OCR
```

要求：

- 点击缓存“消息”后必须确认仍在聊天列表。
- 如果确认失败，清理 `bottom_message` 缓存，回退原流程。
- 防熄屏点击“消息”也复用 `bottom_message`。

预期收益：

- 缓存建立后，每轮列表扫描少一次完整 `list OCR`。

## 8. list OCR 区域缩短

目标：

- 后续列表 OCR 只扫消息主体，不扫顶部标题和底部导航。

动态区域：

```text
list_top = 消息关系底部 + 0.02~0.04
list_bottom = bottom_nav顶部 - 0.02~0.04
list_region = [0.0, list_top, 1.0, list_bottom - list_top]
```

说明：

- `x` 轴保留全宽，保证左侧未读红点、头像、右侧礼物/时间仍可参与行结构判断。
- 不写死 `y` 坐标，客户设备上具体位置不固定。
- 没有顶部锚点或底部导航锚点时，回退当前 `message_list` 配置。
- 缩短区域没有有效行时，回退大范围复扫一次。

## 9. 截图复用

可复用场景：

- `confirm_chat_window()` 后立刻检测新招呼。
- 同一张聊天界面截图中同时检测“新招呼”和“下一条”。
- 点击下一条后的截图，先判断聊天界面，再检测新招呼。
- 发送按钮消失确认后，如果马上找下一条，可以复用最新截图。

必须重新截图的场景：

- 点击目标进入聊天后。
- 点击新招呼后需要确认界面变化时。
- 点击下一条后。
- 上滑后。
- 点击输入框、麦克风、发送后。
- 弹窗被关闭后。

要求：

- 如果弹窗检测没有关闭弹窗，可以返回原图继续使用。
- 如果关闭了弹窗，必须刷新截图。

## 10. 下一条后新招呼前置

当前问题：

- 点击下一条后会先用 `dialogue OCR` 读名字判断是否切人。
- 但如果新页面有“新招呼”，可以直接点击，不需要先读名字。

优化流程：

```text
点击下一条 -> 截图 -> 确认聊天界面 -> 检测新招呼

如果有新招呼：
  点击新招呼
  跳过姓名 OCR
  跳过 message OCR
  继续找下一条

如果没有新招呼：
  做 dialogue_name 小区域 OCR
  判断是否同一人
  不是同一人则进入正常回复流程
```

约束：

- 新招呼仍使用用户选定范围。
- 新招呼匹配结果只允许同一张截图内复用，不做跨轮缓存。
- 找不到下一条时保持原规则：返回聊天列表。

## 11. dialogue OCR 拆分

拆分为两个场景：

- `dialogue_name`：只读顶部名字，用于下一条后判断是否切人。
- `dialogue_message`：只读聊天气泡，用于获取 sender1 最后一段内容。

### 11.1 dialogue_name 区域

来源：

- 当前名字过滤规则已经要求名字中心满足 `center_x=0.3~0.7` 且 `center_y<=user_name_top_ratio`。
- 因此小区域由现有规则反推，不写死坐标。

动态计算：

```text
top_ratio = user_name_top_ratio             # 当前 0.09
center_x_min = user_name_center_x_min_ratio # 当前 0.3
center_x_max = user_name_center_x_max_ratio # 当前 0.7

left = max(0.0, center_x_min - 0.18)
right = min(1.0, center_x_max + 0.18)
top = max(0.0, top_ratio - 0.065)
bottom = min(chat_area_bottom, top_ratio + 0.025)

dialogue_name_region = [left, top, right - left, bottom - top]
```

当前参数估算约为：

```text
x = 0.12~0.88
y = 0.025~0.115
```

但实现必须从配置动态计算。

识别后继续套用现有规则：

- `center_x=0.3~0.7`。
- `center_y<=user_name_top_ratio`。
- 最小长度规则。
- 排除 `数字+km`。
- OCR 结果坐标映射回整屏比例后再判断。

回退：

- 没读到名字。
- 读到明显异常内容。
- 与预期联系人比对结果不可信。
- 以上情况回退完整 `chat_area` dialogue OCR。

### 11.2 dialogue_message 区域

动态底部：

```text
bottom = input_box_y - 0.03~0.06
```

要求：

- `input_box_y` 来自本次启动缓存的输入框位置。
- 偏移使用屏幕比例，不使用固定像素。
- 如果上一条回复打开了输入框，切到下一人后先收回输入框，再计算 message 区域。
- 如果没有 `input_box_y`，回退当前 `chat_area`。
- 如果小区域没有有效 sender1 内容，回退当前 `chat_area` 复扫一次。

## 12. points OCR

决策：

- points OCR 范围由用户手动设置。
- 当前优化不自动计算 points 范围。

实现要求：

- 直接使用用户配置的 points OCR 范围。
- 不自动根据“金币”位置二次缩小。
- 不缓存金币区域。
- 不做 points 范围动态计算。
- 识别失败时按现有“积分未识别”逻辑处理。

## 13. 防熄屏流程

优化点：

- 防熄屏点击“消息”时优先使用 `bottom_message` 缓存。
- 防熄屏复扫可以使用 `list_compact` 区域。
- 防熄屏进入空闲等待后，OCR 复扫间隔从约 5 秒调整为 20 秒，减少空闲状态 OCR 资源消耗。
- 防熄屏点击底部“消息”的间隔也调整为 20 秒一次，避免过于频繁点击。
- 防熄屏过程中遇到弹窗，先关闭弹窗。
- 如果 `list_compact` 无结果，回退大范围 list OCR。

保持不变：

- 首次进入防熄屏读取积分。
- 后续防熄屏只点击一次“消息”。
- 等待期间仍可复扫，有消息就回复。

配置建议：

- 将欢友空闲轮询间隔配置为 `idle_poll_interval_seconds = 20`。
- 将欢友防熄屏点击间隔配置为 `keep_awake_interval_seconds = 20`。
- 只影响进入防熄屏/暂无消息后的复扫频率，不影响正在处理消息时的主流程速度。

## 14. 日志和统计

必须记录：

- 每次 OCR 的 mode、region、耗时。
- 每次模板匹配的 key、是否复用当前截图、耗时。
- 坐标缓存命中次数和失败次数。
- 小区域 OCR 回退完整区域次数。
- 下一条后新招呼快速分支命中次数。
- 单轮回复总耗时。
- 单轮截图次数。
- 单轮 OCR 次数。

日志目的：

- 判断优化是否真的省 OCR。
- 判断是否有小区域漏识别。
- 判断是否因为缓存点击导致异常恢复增加。

## 15. 回退规则

- 小区域 OCR 无结果，不直接失败，先回退大范围。
- 缓存坐标点击后界面没按预期变化，只清对应缓存。
- 新招呼快速分支只调整顺序，不改变原有“找不到下一条就返回列表”的规则。
- 底部消息恢复特例没有缓存 `bottom_nav_region` 时不强行完整 OCR。
- 任何优化开关关闭后，应恢复现有流程行为。

## 16. 实施顺序

1. 增加优化开关和耗时日志。
2. 增加运行态缓存结构。
3. 缓存 `bottom_message`、`bottom_my`、`back`、`input_box`。
4. 从第一次完整 list OCR 结果中缓存 `bottom_nav_region`。
5. 实现底部消息恢复特例。
6. 实现列表扫描顺序优化。
7. 实现 `screen.chat_list` 范围内“消息关系”OCR 判断。
8. 实现 `list_compact` 区域。
9. 实现截图复用。
10. 实现下一条后新招呼前置。
11. 实现 `dialogue_name` 小区域 OCR。
12. 实现 `dialogue_message` 动态区域 OCR。
13. 将防熄屏空闲复扫间隔和点击“消息”间隔都调整为 20 秒。
14. 跑测试和对比日志。
15. 红点快速预筛保持暂缓。

## 17. 测试项

必须测试：

- 正常聊天列表有未读消息。
- 聊天列表无未读消息。
- 首次运行没有任何缓存。
- 已有 `bottom_message` 缓存后的列表扫描。
- 跳到交友/广场/娱乐/我的后，通过底部消息恢复。
- 聊天界面有新招呼。
- 点击下一条后有新招呼。
- 点击下一条后没有新招呼，需要正常 OCR 回复。
- 输入框已弹出后切到下一人，需要收回输入框。
- `dialogue_name` 小区域识别失败后能回退大范围。
- `dialogue_message` 小区域无 sender1 后能回退大范围。
- 黑屏状态不清缓存。
- 无手机状态不清缓存但停止流程。
- 未知界面恢复不主动清缓存。
- 进入防熄屏后，暂无消息复扫间隔约为 20 秒。
- 进入防熄屏后，点击底部“消息”的间隔约为 20 秒。

性能对比：

- 完整 list OCR 平均耗时。
- `list_compact` 平均耗时。
- 完整 dialogue OCR 平均耗时。
- `dialogue_name` 平均耗时。
- `dialogue_message` 平均耗时。
- 单轮截图次数。
- 单轮 OCR 次数。
- 连续 10 个新招呼处理耗时。

## 18. 验收标准

- 缓存建立后，聊天列表常规扫描应从两次 list OCR 降为一次 list OCR。
- 下一条后有新招呼时，不应先跑姓名 OCR。
- 从其他主界面 tab 恢复时，优先点击底部“消息”，而不是直接返回。
- 小区域 OCR 失败时能稳定回退，不触发熔断。
- 日志能看出每轮 OCR 次数、截图次数和耗时。
- 防熄屏空闲状态下不再约 5 秒复扫一次，改为约 20 秒复扫一次。
- 防熄屏点击底部“消息”不再高频触发，改为约 20 秒一次。
- points OCR 使用用户手动配置范围，不出现自动动态调整。
- 红点快速预筛没有进入当前开发实现。
