# 欢友运行流程优化讨论

> 目标：结合当前欢友真实流程，讨论如何提升运行速度、减少 OCR 次数、降低误判。本文是讨论方案，不代表已经全部实现。

## 0. 当前流程前提

当前欢友主流程大致是：

1. `run_once()` 开始。
2. 非空闲状态先检查弹窗，再 `find_unread_target()`。
3. `ensure_list_screen()` 确认聊天列表；如果在聊天界面、我的界面或未知界面，会尝试返回到聊天列表。
4. 恢复特例：如果当前不在聊天界面，并且已缓存 `bottom_nav_region`，用底部导航小范围 OCR 查找“消息”，命中后优先点击底部“消息”恢复到聊天列表。
5. 在聊天列表做 `list OCR`，识别 `message_list` 和 `bottom_nav`。
6. 点击底部“消息”后复扫一次 `list OCR`，再选择有未读的目标。
7. 点击目标进入聊天界面。
8. `_prepare_chat_window()` 先检测并处理“新招呼”；如果没有新招呼，再上滑并确认聊天界面。
9. `read_message()` 用 `dialogue OCR` 读取 sender1 最后一段内容；如果没有 sender1 内容，默认按“你好”处理。
10. 生成回复，点击输入框，点击麦克风，TTS 播放，点击发送。
11. 发送后点击“下一条”，并通过 `dialogue OCR` 读取名字判断是否切换联系人。
12. 如果切到新联系人，继续处理新招呼或正常 OCR 回复；如果没有下一条，返回聊天列表。
13. 无目标时进入防熄屏流程，首次读取积分，后续只点击底部“消息”。

当前模板匹配前提：

- 所有主要模板已经有选定匹配范围，不是全图盲搜。
- 当前配置里已有 `template_match_regions`，包括返回、输入框、麦克风、新招呼、下一条、发送、聊天列表、聊天界面、我的界面等。
- 因此“把模板匹配改成区域化”不是主要优化点；真正的优化重点应放在减少截图、减少 OCR、复用已识别坐标、缩小 OCR 区域和调整流程分支。

## 1. 聊天列表界面判断优化

当前问题：

- 聊天列表模板虽然已有匹配范围，但实际运行中仍可能因为页面轻微变化、活动入口、亮度、截图偏移导致不准。
- 聊天列表顶部有稳定文字“消息关系”，可以作为辅助判断。

建议方案：

- 保留 `screen.chat_list` 模板匹配作为第一层判断。
- 增加当前 `screen.chat_list` 匹配范围内的小区域 OCR 判断。
- 如果在这个范围内 OCR 识别到“消息关系”，直接判定当前在聊天列表。
- 这个范围是用户专门为聊天列表界面匹配选定的范围，不需要再结合底部“消息”或列表行做二次确认。

建议区域：

- 优先使用当前 `screen.chat_list` 的模板匹配范围。
- 不使用全屏 OCR，也不使用其他大范围。

收益：

- 降低聊天列表模板误判。
- 避免未知界面恢复时反复返回。

风险：

- 辅助 OCR 本身也有成本，所以应只在模板判断失败或不确定时使用。
- 这里的前提是 OCR 使用当前 `screen.chat_list` 的选定范围，而不是全屏或其他大范围。

建议优先级：高。

## 2. 底部消息恢复特例

当前问题：

- 有时程序可能跳转到欢友主界面的其他 tab。
- 这类页面不一定能匹配聊天列表，也不一定应该直接点返回。
- 但只要底部导航栏 `bottom_nav` 中能 OCR 到“消息”，点击“消息”就能恢复到聊天列表。

建议方案：

- 在 `ensure_list_screen()` 中增加一个恢复特例。
- 如果当前没有匹配到聊天界面，并且底部导航小范围 OCR 能识别到“消息”，优先点击“消息”。
- 点击“消息”后重新截图，再用 `screen.chat_list` 模板或 `screen.chat_list` 范围内的“消息关系”OCR 确认聊天列表。
- 只有底部“消息”也识别不到时，再走原来的未知界面返回恢复。
- 这个底部导航 OCR 不使用完整 `list OCR` 范围，应优先使用缓存的 `bottom_nav_region`。

底部导航范围缓存：

- 第一次完整 `list OCR` 通常能识别到 `bottom_nav` 中“交友/广场/娱乐/消息/我的”的 bounds。
- 拿到这些 bounds 后，计算并缓存 `bottom_nav_region`，用于后续未知界面恢复时的小范围 OCR。
- `bottom_nav_region_top = min(bottom_nav各项top) - 0.02`。
- `bottom_nav_region_bottom = max(bottom_nav各项bottom) + 0.02`。
- `bottom_nav_region = [0.0, top, 1.0, bottom - top]`。
- 所有偏移都使用屏幕比例，不使用固定像素。
- 如果还没有 `bottom_nav_region` 缓存，则本次恢复特例可以跳过，直接走原未知界面返回；不要为了这个特例跑完整 list OCR。

触发条件：

- 当前不是聊天界面。
- 当前不是无手机、黑屏等异常界面。
- 已经缓存 `bottom_nav_region`。
- 在 `bottom_nav_region` 小范围 OCR 中识别到 name 为“消息”的项。

收益：

- 从“交友/广场/娱乐/我的”等主界面 tab 恢复更直接。
- 减少误点返回导致退出页面或触发异常恢复。

风险：

- 这一步仍然会占用一次 OCR，但只扫缓存的底部导航小范围，并且只在界面判断失败或不确定时触发，不作为每轮常规扫描。
- 没有缓存 `bottom_nav_region` 时不要强行完整 OCR，避免恢复特例反而增加主流程 OCR 压力。

建议优先级：高。

## 3. 单次启动内缓存固定坐标

当前情况：

- 模板匹配已有选定范围，但每次仍要截图、裁剪、模板匹配。
- 底部导航“消息”“我的”目前依赖 `list OCR` 结果点击。
- 输入框、返回、底部导航位置在单次启动和同一设备上通常稳定。
- “下一条”“发送”“麦克风”的位置可能随页面状态、输入状态或按钮样式变化，不建议做坐标缓存。

建议方案：

- 增加单设备运行态缓存，只在当前进程内生效，不写死到配置文件。
- 第一次模板匹配或 OCR 成功后，缓存坐标。
- 后续同一界面优先使用缓存坐标点击。
- 缓存点击失败、界面不符合预期、连续 StepUnavailable 或模板即时校验失败后，清空对应缓存。

建议优先缓存：

- `bottom_message`：底部“消息”。
- `bottom_my`：底部“我的”。
- `back`：返回。
- `input_box`：输入框。
- `chat_name_point`：聊天对象名字坐标，用于收回输入框。

只做当前截图内复用，不做跨轮坐标缓存：

- `new_greeting`：新招呼按钮可以和“下一条”出现在同一张图里，适合同图复用匹配结果，但不建议跨轮固定坐标点击。
- `next_message`：下一条按钮位置可能变化，应继续使用当前选定范围即时匹配；同一张截图里已匹配到的位置可以立即复用。
- `send`：发送按钮位置可能变化，应继续使用当前选定范围即时匹配；同一张截图里已匹配到的位置可以立即复用。
- `microphone`：麦克风位置可能变化，应继续使用当前选定范围即时匹配；同一张截图里已匹配到的位置可以立即复用。

不建议缓存：

- 不建议把“新招呼”“下一条”“发送”“麦克风”的坐标作为跨轮运行态缓存长期复用。

收益：

- 节省重复模板匹配和底部导航 OCR。
- 对防熄屏点击底部“消息”、打开“我的”、返回列表、收回输入框这几个高频动作收益明显。

风险：

- 缓存不能跨设备、跨进程使用。
- 输入框弹出、键盘状态变化时，输入框位置也可能变化，需要按状态区分缓存或失败后重新匹配。

建议优先级：高。

## 4. 截图复用优化

当前问题：

- 日志里经常出现 `capture_pre_move` 单次 3 秒以上，截图成本可能比模板匹配更高。
- 当前流程中有些步骤截图间隔很近，例如确认聊天界面、检测新招呼、检测下一条、读取名字。
- “新招呼”和“下一条”按钮可能同时出现在同一张聊天界面截图里，这张图可以同时用于两个模板匹配。

建议方案：

- 同一步骤内如果没有发生点击、滑动、弹窗关闭、输入框弹出等界面变化，应复用上一张截图。
- 点击、滑动、TTS 后必须重新截图。
- 弹窗检测如果没有关闭任何弹窗，可以返回原图继续用；如果关闭过弹窗，必须刷新截图。

适合复用的场景：

- `confirm_chat_window()` 后立刻检测新招呼。
- 检测到新招呼的同一张截图，可以继续检测“下一条”按钮位置，避免点击新招呼前后重复截图只为了找下一条。
- 点击下一条后的截图，先判断聊天界面，再检测新招呼。
- 发送按钮消失确认后，如果马上找下一条，可以复用最新截图。

不适合复用的场景：

- 刚点击目标进入聊天。
- 刚点击新招呼后，如果要确认界面是否变化、是否还在聊天界面或是否切到下一条，必须重新截图；但点击前同一张图可同时用于找新招呼和下一条。
- 刚点击下一条。
- 刚上滑。
- 刚点击输入框、麦克风、发送。

收益：

- 减少机械臂截图耗时。
- 整体速度提升可能比模板优化更明显。

建议优先级：高。

## 5. list OCR 范围缩短

当前情况：

- `message_list` OCR 默认区域是 `x=0.0~1.0, y=0.1~0.9`。
- 第一次 list OCR 会拿到 `bottom_nav`，包括“消息”“我的”等位置。
- 当前列表未读识别还包含红点检测、白字校验、系统项过滤。
- 参考截图 `20260530_233729_full.jpg`，聊天列表主体大致从第一条头像/名字开始，到底部导航上方结束；顶部“消息/关系”和底部导航都不需要进入后续列表主体 OCR。

建议方案：

- 第一次进入聊天列表仍使用当前较大区域，保证拿到底部导航和列表结构。
- 一旦在 `screen.chat_list` 选定范围内识别到“消息关系”，并且第一次 list OCR 拿到底部“消息”，就缓存列表主体区域。
- 后续 list OCR 只扫列表主体，不扫顶部导航和底部导航。
- 底部“消息”“我的”使用缓存坐标，不再依赖每轮 list OCR。

建议动态区域：

- `list_top = 消息关系底部 + 0.02~0.04`。
- `list_bottom = bottom_nav顶部 - 0.02~0.04`。
- `x` 轴建议仍保留接近全宽，例如 `x=0.0~1.0`，因为左侧头像红点、右侧礼物/时间都可能辅助行边界判断。
- 如果没有顶部锚点，仍使用当前 `message_list` 配置。
- 如果缩短区域没有识别到有效行，回退到当前大范围复扫。

参考图说明：

- `20260530_233729_full.jpg` 这张图可以证明列表主体确实位于顶部“消息关系”和底部导航之间。
- 但客户设备上的具体 y 坐标不一定一致，所以不建议写死 `0.105~0.865`。
- 这里应使用 OCR 识别到的“消息关系”和 `bottom_nav` 位置动态计算。

收益：

- 降低 list OCR 耗时。
- 减少底部导航、活动入口、系统入口被拼进 `message_list`。

风险：

- 如果顶部活动位变化，动态区域可能偏窄。
- 必须保留大范围兜底。

建议优先级：高。

## 6. 列表扫描顺序优化

当前情况：

- 当前 `find_unread_target()` 在聊天列表中会先跑一次 `list OCR`。
- 第一次 `list OCR` 的一个重要作用是拿到底部 `bottom_nav` 中“消息”的位置。
- 拿到“消息”后会点击一次底部“消息”，然后再截图复扫一次 `list OCR`，最终用复扫结果选择未读目标。

可优化点：

- 当本次运行已经缓存了底部“消息”坐标后，不需要先跑一遍 `list OCR` 只是为了找“消息”。
- 后续进入聊天列表时，可以先点击缓存的底部“消息”坐标，再截图跑一次 `list OCR`。
- 这样后续列表扫描从“两次 list OCR”减少为“一次 list OCR”。

建议方案：

- 第一次没有缓存 `bottom_message` 时，仍走当前流程：`list OCR -> 点击消息 -> list OCR复扫`。
- 一旦成功拿到 `bottom_message`，后续流程改为：`点击缓存消息 -> 截图 -> list OCR`。
- 如果点击缓存消息后界面不符合预期，清掉 `bottom_message` 缓存，回退当前完整流程。
- 防熄屏流程也复用同一个 `bottom_message` 缓存。

收益：

- 后续每轮聊天列表扫描少一次完整 `list OCR`。
- 对无消息空轮询和高频列表扫描收益明显。

风险：

- 如果缓存的“消息”坐标点偏，可能导致没有回到消息 tab；所以点击后必须确认仍在聊天列表，再继续 list OCR。

建议优先级：高。

## 7. points OCR 范围缩短

当前决策：

- points OCR 范围由用户手动设置。
- 这一部分不纳入当前自动优化。
- 程序只需要使用用户配置的 points OCR 范围，不再自动动态计算或缓存金币区域。

当前情况：

- 防熄屏首次进入“我的”界面读取金币。
- 金币位置与“我的收益”在一起。
- 当前目标是取“金币”前面的数字，再除以 10 显示到主 UI。

不做的方案：

- 不自动根据“金币”位置二次缩小范围。
- 不缓存金币区域。
- 不做 points 范围动态计算。

使用方式：

- 直接使用用户手动设置的 points OCR 范围。
- 如果用户配置范围识别失败，按现有积分未识别逻辑处理。

收益：

- 避免自动范围推断和用户手动设置冲突。
- 配置责任更清晰，后续调试更直接。

风险：

- 用户配置范围过窄时可能识别不到，需要通过模板/配置管理界面调整。

建议优先级：不纳入当前优化。

## 8. dialogue OCR 范围缩短

当前情况：

- `dialogue` OCR 默认区域在代码默认值里是 `x=0.0~1.0, y=0.1~0.8`，当前欢友配置实际已调整为接近 `x=0.0~1.0, y=0.0~0.9`。
- 进入聊天界面后，如果没有新招呼，会先上滑，再做 dialogue OCR。
- 发送后切到下一人时，会读取名字判断是否同一个人。
- 当前代码里读取名字并不是单独的小区域 OCR，而是仍然跑 `chat_area` 的 dialogue OCR，然后用 `user_name_top_ratio=0.09` 和 `center_x=0.3~0.7` 从 OCR 结果里筛顶部名字。

建议方案：

- 正常读取消息时，dialogue OCR 区域底部可以根据输入框位置收窄。
- 输入框位置如果已在本轮启动中缓存，可以用 `input_box_y` 往上减一个安全距离，作为 `dialogue_message` 的动态底部边界。
- 顶部可以根据聊天标题栏或 user_name 区域收窄。
- 姓名校验不需要完整 `chat_area` dialogue OCR，可以改成真正的“顶部名字小区域 OCR”。
- 顶部名字小区域不是拍脑袋写固定坐标，而是用当前已有的名字过滤规则反推出来。

建议拆分两个 OCR 场景：

- `dialogue_name`：只扫顶部名字区域，用于下一条后判断是否切人；继续保留 `center_x=0.3~0.7`、`user_name_top_ratio`、排除 `数字+km` 等名字过滤规则。
- `dialogue_message`：只扫聊天气泡区域，用于读取 sender1 内容；底部优先用缓存的输入框 y 坐标动态计算。

`dialogue_name` 动态区域建议：

- 区域来源：当前名字判断规则已经规定“名字中心点必须在 `center_x=0.3~0.7`，并且 `center_y <= user_name_top_ratio`”。所以 OCR 裁剪区域可以围绕这块区域加安全边距。
- 读取配置：`top_ratio = user_name_top_ratio`，当前是 `0.09`。
- 读取配置：`center_x_min = user_name_center_x_min_ratio`，当前是 `0.3`。
- 读取配置：`center_x_max = user_name_center_x_max_ratio`，当前是 `0.7`。
- `left = max(0.0, center_x_min - 0.18)`。
- `right = min(1.0, center_x_max + 0.18)`。
- `top = max(0.0, top_ratio - 0.065)`。
- `bottom = min(chat_area_bottom, top_ratio + 0.025)`。
- 最终区域：`[left, top, right - left, bottom - top]`。
- 按当前参数估算，区域大约是 `x=0.12~0.88, y=0.025~0.115`，但实现时不要写死这个值，要从配置动态算。
- OCR 后仍然把结果映射回整屏坐标，再套现有名字过滤规则：`center_x=0.3~0.7`、`center_y<=0.09`、最小长度、排除 `数字+km`。
- 如果 `dialogue_name` 没读到名字、读到明显异常内容，或与预期联系人比对失败不可信，再回退当前完整 `chat_area` dialogue OCR。

`dialogue_message` 动态区域建议：

- `top`：聊天标题栏下方，仍可沿用当前 `chat_area` 顶部或根据名字区域底部向下偏移。
- `bottom = input_box_y - 0.03~0.06`，这里的偏移用百分比，不用固定像素。
- 如果没有缓存到输入框 y 坐标，则回退当前 `chat_area` 配置。
- 如果动态区域没有识别到有效 sender1 内容，也回退当前 `chat_area` 配置复扫一次。

收益：

- 下一条校验名字更快。
- 读取聊天内容时减少输入框、推荐灵感、底部按钮干扰。

风险：

- user_name 识别有时会读到下面的字，所以顶部名字区域必须继续限制 `center_x=0.3~0.7`，并排除 `数字+km`。
- 输入框弹出状态会改变底部区域；如果上一条回复把输入框点出来了，切到下一人后需要先收回输入框，再用输入框 y 坐标计算 `dialogue_message` 区域。
- “输入框 y 坐标”只能作为本次启动内的动态参考，不能写死到配置。

建议优先级：中高。

## 9. 下一条后新招呼分支前置

当前情况：

- 点击“下一条”后，目前为了确认是否切人，会走 `dialogue OCR` 读取名字。
- 如果新页面有“新招呼”按钮，其实可以直接点击新招呼，不需要先读取名字。
- 当前新招呼模板已经有用户选定范围，不是全图检测。

建议方案：

- 点击下一条后刷新截图。
- 先确认仍在聊天界面。
- 立即在已配置的新招呼范围内检测“新招呼”。
- 如果有新招呼，直接点击新招呼，跳过本轮姓名 OCR 和 message OCR。
- 如果没有新招呼，再做顶部名字小区域 OCR 判断是否切人。
- 如果不是同一人，再按正常回复流程：必要时收回输入框、上滑、message OCR、生成回复、发送、下一条。

收益：

- 连续新招呼时大幅减少 OCR。
- 避免“新招呼场景”无意义读取名字。

风险：

- 新招呼误匹配会错点，但已有选定范围，风险可控。
- 点击新招呼后如果没有下一条，要按当前规则返回聊天列表。

建议优先级：高。

## 10. 防熄屏流程优化

当前情况：

- 无目标后进入防熄屏。
- 首次进入防熄屏会读取积分。
- 后续防熄屏已经改为只点击一次底部“消息”。
- 防熄屏期间仍会复扫列表，有消息则回复。

建议方案：

- 防熄屏期间优先使用缓存的底部“消息”坐标点击，不再为了点击消息跑底部导航 OCR。
- 防熄屏复扫可以使用缩短后的 list 区域。
- 如果检测到弹窗，先关闭弹窗再继续。
- 如果缩短 list 区域无结果，再回退大范围 list OCR。

收益：

- 空闲时资源消耗更低。
- 避免防熄屏阶段反复 OCR 底部导航。

建议优先级：中高。

## 11. 未读识别快速预筛

当前决策：

- 这一部分先不做改动。
- 等现有红点检测和 list OCR 在客户环境测试完成后，再决定是否进入开发。
- 当前优化批次不要把“红点快速预筛”作为实现任务。

当前情况：

- list 模式已结合 OCR 行结构和红点检测。
- 红点检测要求红块内存在白色数字像素，避免头像或标签误判。

后续可选方案：

- 保持当前 list OCR 作为最终判断。
- 可以增加快速预筛：先在列表行左侧区域找红色未读块。
- 如果完全没有未读红点，直接进入防熄屏，不必完整 list OCR。
- 如果有红点，再跑 list OCR 取 name/content/bounds。

收益：

- 无消息时速度提升明显。

风险：

- 红点漏检会导致漏回复，所以这一步只能在红点规则稳定后再做。
- 现阶段仅保留为后续实验项，不作为当前批次改动。

建议优先级：暂缓。

## 12. 运行态缓存结构建议

建议新增单设备、单线程运行态缓存：

```text
runtime_cache = {
  screen_anchors: {
    chat_list_title: (x, y),
    bottom_message: (x, y),
    bottom_my: (x, y)
  },
  template_points: {
    back: (x, y),
    input_box: (x, y)
  },
  current_frame_matches: {
    new_greeting: (x, y),
    next_message: (x, y),
    send: (x, y),
    microphone: (x, y)
  },
  non_cross_round_cached_templates: [
    "new_greeting",
    "next_message",
    "send",
    "microphone"
  ],
  ocr_regions: {
    bottom_nav_region: (left, top, right, bottom),
    list_compact: (left, top, right, bottom),
    dialogue_name: (left, top, right, bottom),
    dialogue_message: (left, top, right, bottom),
    points_configured: (left, top, right, bottom)
  },
  current_chat: {
    name: "...",
    name_point: (x, y),
    input_box_opened: true/false
  }
}
```

缓存失效条件：

- 线程重启。
- 点击后界面没有按预期变化。
- 连续 StepUnavailable。
- 缓存坐标对应的模板即时校验失败。
- 用户暂停进程后重新启动，重新建立本次运行缓存。

不作为缓存失效条件：

- 黑屏、无手机、未知界面恢复：这些只影响当前轮恢复流程，不主动清空缓存。
- 设备或 app 切换：用户必须暂停进程后重新启动，缓存会随新线程自然重建。
- 截图尺寸变化：用户端运行过程中正常不会发生。
- 用户重新设置模板范围：用户端不提供模板范围设置入口。

## 13. 实现护栏和日志建议

这批优化会改变 OCR 范围、截图复用和分支顺序，建议实现时加护栏，方便实测和回滚。

建议增加开关：

- `enable_runtime_coordinate_cache`：是否启用运行态坐标缓存。
- `enable_screenshot_reuse`：是否启用同一步骤截图复用。
- `enable_compact_list_ocr_region`：是否启用缩短后的 list OCR 区域。
- `enable_dialogue_name_region`：是否启用顶部名字小区域 OCR。
- `enable_dialogue_message_region`：是否启用聊天内容动态区域 OCR。
- `enable_next_new_greeting_fast_path`：是否启用下一条后先检测新招呼。

建议日志指标：

- 每次 OCR 的 mode、region、耗时。
- 每次模板匹配的 key、是否使用当前截图复用、耗时。
- 坐标缓存命中次数和失败次数。
- 小区域 OCR 回退完整区域的次数。
- 下一条后新招呼快速分支命中次数。
- 单轮回复总耗时、截图次数、OCR 次数。

建议回退原则：

- 小区域 OCR 没有结果，不直接判定失败，先回退当前大范围。
- 缓存坐标点击后界面没按预期变化，只清对应缓存，不清全部缓存。
- 新招呼快速分支只改变顺序，不改变“找不到下一条就返回列表”的原有规则。
- 所有优化开关默认可以逐项开启，先测收益最高、风险最低的项。

## 建议落地顺序

1. 先增加优化开关和耗时日志，确保每项优化都能单独开关、计数和回退。
2. 增加底部消息恢复特例：不在聊天界面但 `bottom_nav` 识别到“消息”时，优先点“消息”恢复列表。
3. 增加运行态坐标缓存，先缓存底部“消息”“我的”“返回”和输入框；不缓存“下一条”“发送”“麦克风”。
4. 优化列表扫描顺序：已有 `bottom_message` 缓存时，先点“消息”再做一次 list OCR，避免先扫再复扫。
5. 下一条后新招呼分支前置：有新招呼就直接点击，不先读名字。
6. 拆分 `dialogue_name` 和 `dialogue_message`，下一条校验只扫顶部名字小区域。
7. 增加 `screen.chat_list` 选定范围内的“消息关系”OCR 判断；识别到即可直接判定聊天列表。
8. 缩短 list OCR 区域，并保留大范围兜底。
9. 做截图复用，优先减少连续 confirm/detect 之间的重复截图。
10. 红点快速预筛暂缓，等测试完成后再决定是否开发。

## 当前不建议直接做的点

- 不建议删除现有模板范围机制。
- 不建议在全屏或未限定范围内只靠“消息关系”判断聊天列表；但在 `screen.chat_list` 选定范围内识别到“消息关系”可以直接判定。
- 不建议把运行态缓存坐标写死到配置文件。
- 不建议立刻用红点预筛完全替代 list OCR。
- 不建议在输入框弹出状态下复用旧 dialogue 区域。

## 需要实测的数据

- 当前完整 list OCR 平均耗时。
- 缩短 list 区域后的平均耗时和漏检率。
- 当前完整 dialogue OCR 平均耗时。
- 顶部名字小区域 OCR 平均耗时和名字识别准确率。
- 新招呼分支前置后，连续处理 10 个新招呼的耗时。
- 坐标缓存点击成功率。
- 截图复用后单轮流程减少的截图次数。

## 结论

结合当前代码，最有价值的优化不是重新做模板范围，而是：

- 单次启动内缓存已匹配到的固定坐标。
- 减少不必要截图。
- 下一条后先检测新招呼，有新招呼直接点，不先跑姓名 OCR。
- 把姓名 OCR 和消息 OCR 拆成两个更小的区域。
- list 和 dialogue 做动态缩短区域，并保留大范围兜底；points 使用用户手动配置范围，不做自动动态缩小。

这样既能利用现有模板选区，又能把主要耗时从 OCR 和截图上降下来。
